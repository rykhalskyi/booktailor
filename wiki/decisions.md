# Decisions

Append-only decision record. The "why" lives here; the full change history lives in git.
- [2026-10-22] D-01 — Book is the workspace and Composition is the generated final document — because the draft overloaded book for both concepts
- [2026-10-22] D-02 — Support multiple books per user with no sharing in the MVP — because workspaces must be independent before permissions are added
- [2026-10-22] D-03 — Store assets in a visible dedicated Nextcloud folder — because users should be able to browse and use Nextcloud editors directly
- [2026-10-22] D-04 — Use Asset as the umbrella term for Markdown files inside a chapter — because they can be sources, intermediates, or results
- [2026-10-22] D-05 — Use native Nextcloud versions plus sidecar check-in metadata — because native history is reliable and messages are app-level data
- [2026-10-22] D-06 — Ship Markdown composition first and add DOCX later — because the compose service is not yet designed
- [2026-10-22] D-07 — Implement only the draft chapter movement rules in the MVP — because arbitrary reparenting adds complexity without proven need
- [2026-10-22] D-08 — Allow structures to include chapters independently — because outputs may need a child without its parent
- [2026-10-22] D-09 — Select composition assets with tag-based rules — because tags already classify sources, summaries, and terms
- [2026-10-22] D-10 — AI tools propose changes and the user confirms them — because structural writes must remain intentional and auditable
- [2026-10-22] D-11 — Define the compose contract now and build the separate service later — because the MVP can compose Markdown locally
- [2026-10-22] D-12 — Build the core domain before structures, composition, and AI — because every later feature depends on books, chapters, and assets
- [2026-10-23] D-13 — Visible folders mirror the canonical chapter tree and DB stores Nextcloud file IDs — because users browse in Files while stable file IDs survive renames and moves
- [2026-10-23] D-14 — The draft's default chapter is interpreted as the default structure; there is no separate default chapter — because the draft conflated two concepts
- [2026-10-23] D-15 — Tags are scoped per book in the MVP — because vocabularies should not leak between independent workspaces
- [2026-10-23] D-16 — Images live in a chapter-level images/ subfolder and are referenced by relative paths — because assets in a chapter share images and composition resolves them uniformly
- [2026-10-23] D-17 — Structure entries store inclusion and per-structure sibling position; effective parents are derived at read time — because storing derived parentage would drift from the canonical tree
- [2026-10-23] D-18 — Deleting chapters and assets moves files to native Nextcloud trash while app metadata cascades — because native trash is the expected recovery path
- [2026-10-23] D-19 — Store check-in messages in native files_versions metadata instead of an asset_version_metadata sidecar table — because Nextcloud 31+ exposes per-version metadata including author, removing duplicate state and drift (supersedes the sidecar part of D-05)
- [2026-10-23] D-20 — Open Markdown assets in the Nextcloud Text app via the Files URL openfile parameter, and observe saves through NodeWrittenEvent — because Text saves through the native file API and no custom editor is needed
- [2026-10-23] D-21 — Attach check-in messages to the current native revision after editing and include the current revision in BookTailor's history — because Text autosaves and native version files represent prior content; the message stays with the content it describes and moves into history on the next save
- [2026-10-24] D-22 — Use Langfuse's OTLP endpoint with x-langfuse-ingestion-version 4 and the v2 prompt/observation APIs; do not use the deprecated ingestion or legacy trace APIs — because the self-hosted Langfuse 4 runs in events_only mode where the legacy read APIs are unavailable and prompt links only appear through the v2 observation fields
- [2026-10-24] D-23 — Store BYOK keys encrypted with Nextcloud's ICrypto in a per-user protected record and expose only masked values — because keys must never be returned by the API or written to logs
- [2026-10-24] D-24 — Run composition as a QueuedJob that persists state in the compositions row, claims work with a conditional update, and retries only on explicit request — because QueuedJob removes itself before run and provides no retry after a failure
- [2026-10-24] D-25 — Put only the composition id in the compose job argument and load the book, structure, rules, and assets inside the worker under the owner's user folder — because job arguments are visible in the job list and the stored graph must stay authoritative
- [2026-10-24] D-26 — Version the app's OCS API under /api/v1 — because the MVP surface will grow and clients need a stable prefix
- [2026-10-24] D-27 — Order the T1 canonical chapter tree by chapter id and keep per-structure sibling order only in structure_chapters — because the T0 schema stores order per structure and T1 does not reorder yet
- [2026-10-24] D-28 — Load only BookTailor and files_versions in the PHPUnit bootstrap with TEST_DONT_LOAD_APPS=1 — because the dev server has an unrelated incomplete files_external schema and app tests must be isolated
- [2026-10-24] D-29 — Defer chapter movement, custom structure writes, and raw content endpoints to T3/T4 — because T1 delivers the core book, chapter, asset, tag, and version lifecycle first
- [2026-10-24] D-30 — Keep openapi.draft.yaml as the reviewed contract while openapi.json stays the generated skeleton until controller route docblocks are complete — because the extractor requires full per-route annotations
- [2026-10-24] D-31 — Render asset lists in a right-hand pane for the selected chapter instead of nesting rows under every tree node — because it keeps the tree compact and loads assets only for the active chapter while still giving a per-chapter list
- [2026-10-24] D-32 — Keep T2 state in a module-level useLibrary composable instead of adding Pinia — because one authoring screen shares state across components and the app has no cross-screen store needs
- [2026-10-24] D-33 — Route all create/rename prompts and destructive confirmations through one DialogHost with typed dialog state — because recursive tree nodes should not own modal state and every delete must pass one confirmation path
- [2026-10-24] D-34 — Use a small fetch-based OCS client with generateOcsUrl and the request token instead of adding @nextcloud/axios — because the app has a limited endpoint set and the client already owns envelope and error handling
- [2026-10-24] D-35 — Guard selection requests with a monotonic epoch and keep asset loading per chapter — because out-of-order book/chapter responses must never overwrite the current selection and a shared loading flag flashes the wrong empty state
- [2026-10-24] D-36 — Add vue-tsc to the frontend verification loop and build file links through generateUrl — because Vite does not typecheck and hardcoded /index.php paths break subdirectory installs
- [2026-10-25] D-37 — Compute structure-based numbering server-side in StructureTreeBuilder + NumberingService and return number on chapter nodes — because composition and UI must share one numbering definition
- [2026-10-25] D-38 — Start each new custom structure as a copy of the default structure — because users need a predictable starting point and the copy preserves the full chapter inclusion and sibling order
- [2026-10-25] D-39 — Require every chapter exactly once in structure entry replacement and normalize positions per canonical sibling group — because writes must be atomic, deterministic, and preserve the default structure invariant
- [2026-10-25] D-40 — Let new chapters inherit inclusion from their canonical parent in custom structures and include new roots — because hidden branches should stay hidden without making root additions invisible
- [2026-10-25] D-41 — Keep chapter PATCH as rename-or-move and detect an explicit parentId key while rejecting combined rename and move requests — because an explicit null must promote to the book root and omitted parentId must leave the parent unchanged
- [2026-10-25] D-42 — Move the visible chapter folder with the canonical hierarchy and append the moved chapter to every structure sibling group — because storage mirrors the canonical tree and per-structure order must stay deterministic
- [2026-10-25] D-43 — Put structure management in an in-app view with immediate entry saves and a numbering preview — because inclusion and order changes should appear in the shared tree immediately and users need to see the resulting numbers
- [2026-10-25] D-44 — Offer canonical chapter moves through an allowed-target picker in the structure manager and revalidate the target server-side — because users should only see legal moves while the server remains authoritative
- [2026-10-25] D-45 — Order effective siblings by canonical slots, promoting the children of excluded chapters into the excluded chapter's position — because positions from different canonical sibling groups are not comparable when an ancestor is excluded
- [2026-10-25] D-46 — Track the structure id loaded into the manager editor and refuse entry writes when it does not match the selected structure — because a failed load must never copy one structure's entries into another
- [2026-10-25] D-47 — Launch Markdown assets in the Files/Text flow with dir + openfile derived from Asset.path — because the editor spike verified that URL and no Text-specific API is needed
- [2026-10-25] D-48 — Observe NodeWrittenEvent only to advance asset updated_at and keep check-in explicit from the history dialog — because Text autosaves and creating app-level versions or prompts per write would duplicate native versioning
- [2026-10-25] D-49 — Expose raw asset content and version content through the OCS API — because the T1-deferred endpoints are needed for history previews and API clients
- [2026-10-25] D-50 — Publish editor and version capabilities from the server and hide or disable check-in/history when unavailable — because Text and files_versions can be disabled and the UI must degrade like the spike requires
- [2026-10-25] D-51 — Filter assets by tag client-side within the selected chapter and manage tags in an in-app view — because tags are already serialized on assets and the MVP has no cross-chapter search requirement
- [2026-10-25] D-52 — Measure chapter history per asset through a picker in the chapter menu — because versions belong to files and a chapter can contain several assets
- [2026-10-25] D-53 — Store tag colors as hex values from a fixed 10-color palette and derive readable chip text on the client — because one palette shared by the manager, asset list, and assignment dialog keeps tags consistent while contrast stays correct
- [2026-10-25] D-54 — Move tag management into the app navigation below books and render the selected chapter's assets beside the tree — because tags are a per-book management surface and asset tagging needs a persistent chapter asset list, which the tree-only layout hid
- [2026-10-25] D-55 — Put asset management in a dedicated view opened by Edit assets in the chapter menu and keep the main screen tree-only (supersedes the side-pane part of D-54) — because the user wants chapter assets managed as their own screen with an explicit back path
- [2026-10-26] D-56 — Evaluate composition rules by priority ascending and use the first non-fallback rule with a matching asset, falling back only when no normal rule matches — because chapters need deterministic asset selection with an explicit last resort
- [2026-10-26] D-57 — Emit a heading for a chapter that matches no rule and fail the composition only when zero assets match overall — because empty chapters are legitimate while an all-empty output is not useful
- [2026-10-26] D-58 — Treat an empty composition rule list as select-all assets in filename order — because a baseline whole-book composition should not require tagging every asset
- [2026-10-26] D-59 — Render composition headings as # book, ## depth-one chapters, and deeper levels up to ###### with structure numbering — because output must mirror the selected structure and stay valid Markdown
- [2026-10-26] D-60 — Copy composed images to a shared compositions/images folder with <name>-<fileId> names and rewrite Markdown and HTML references — because deterministic names make retries idempotent and collision-free
- [2026-10-26] D-61 — Name outputs <structure-or-hint-slug>-<UTC timestamp>.md and allow retry only for failed or 30-minute-stale rows — because naming and recovery must be predictable without automatic retries
